# WhatToOffload

[English](README.md)

**把任务写成 Skill 后，反复执行仍可能消耗大量 Agent 推理资源。**

Skill 把经验和操作步骤交给 Agent，但只要流程仍由 Agent 逐步推进，它就需要反复读取上下文、决定下一步、调用工具、检查结果。即使 Skill 已经带有辅助脚本，剩下的调度和判断也可能继续占用大量 Token 和时间。

**WhatToOffload 希望把任务进一步交给脚本、Jev 和 LLM 服务执行，减少对 Agent 持续推理和调度的依赖，优化重复执行的消耗。**

本项目本身也是一个 Skill。它指导 Agent 分析已有任务，找出值得替换的步骤，设计新的分工，并在获得授权后实现和测试。改造后的程序负责日常执行；仍需要开放探索、与用户协商或处理超出能力范围的问题，再交回 Agent。

## 怎样进一步卸载任务

这里的“卸载”，就是把原本每次都要由 Agent 推进的工作，变成程序可以直接执行的步骤。

| 任务中的工作 | 可以交给谁 | 需要检查的条件 |
| --- | --- | --- |
| 读取文件、调用已有接口、计算、去重、校验和保存结果 | 脚本与现有工具 | 规则是否明确，能否识别不支持的输入 |
| 判断一段描述属于哪一类、某个候选是否符合条件 | Jev | 问题是否足够具体，候选和上下文是否充分 |
| 解释复杂材料、生成说明、处理需要额外推理的情况 | LLM 服务 | 是否提供了必要证据，输出能否验证，调用是否有预算 |
| 目标发生变化、需要重新规划、与用户协商 | Agent 或人工 | 是否仍然需要开放探索和持续对话 |

Jev 是 TypeSafe 提供的模型，适合回答范围明确、结果可直接交给代码使用的判断题，例如从候选中选择一项或判断一个条件是否成立。LLM 服务则通过 API 承担需要生成或更复杂推理的步骤。程序负责连接这些步骤、传递证据、处理重试和保存结果。

**卸载不是消除全部模型推理，而是把必要的推理放到合适的位置。** 并非每个任务都需要同时使用三种执行方式，也不需要在每次 Jev 判断后再让 LLM 复核。

## 一个例子

假设你每周都让 Agent 整理供应商报价：读取文件、计算金额、判断条款、筛选候选，最后写一份说明。

WhatToOffload 可以帮助你把这项工作拆成：

1. **脚本**读取文件、检查材料是否齐全，并按明确规则计算金额。
2. **Jev**根据条款原文，判断它是否符合已经定义好的要求。
3. **LLM 服务**处理脚本和 Jev 无法可靠解决的材料，并根据已验证结果生成说明。
4. **程序**汇总结果和未解决的问题；需要补充材料或改变目标时交回 Agent。

替换也有代价：脚本可能漏掉陌生格式，Jev 无法从缺失的候选中选出正确答案，LLM 的补充处理仍会增加成本。因此，方案必须同时说明如何发现这些问题、何时补充证据，以及什么时候停止并交回处理。

## 怎么使用，会得到什么

把已有会话、任务说明、代码或执行记录提供给能够读取本 Skill 的 Agent。入口是 [SKILL.md](SKILL.md)。可以从下面的请求开始：

```text
使用 $what-to-offload 分析这个任务。
找出哪些具体步骤可以交给脚本、Jev 或 LLM 服务，哪些应继续留给 Agent。
说明每种替换的收益、可能损失的能力，以及如何验证。先给方案，不修改代码。
```

它会先检查已有材料，通常给出最多三个优先建议。每个建议说明原来由 Agent 做什么、准备交给谁、替换的前提、收益与风险，以及验证方法。

选中方案后，可以继续要求：

```text
展开第一个方案：给出步骤之间的关系、每步需要的输入、输出、异常处理和测试方法。
```

设计确认后，再要求实施：

```text
按这个方案实现，保留项目现有技术栈。
先验证结果质量，再比较成本和耗时，并说明仍需 Agent 处理的情况。
```

实现可以是现有项目中的函数、可直接调用的执行程序（runner），或接入已有工作流系统的步骤。真实 API 调用和外部操作须在用户授权范围内进行。

## 怎样判断一次替换值得做

WhatToOffload 按七步检查，避免只看调用次数或价格：

1. **观察原来的行为**：具体替换哪项工作？它依赖哪些上下文？
2. **确定验收要求**：哪些结果必须正确、完整、有证据？
3. **比较执行方式**：脚本、Jev、LLM 各能做什么，会失去什么能力？
4. **明确证据输入**：候选是否齐全，来源和上下文是否保留？
5. **设计异常处理**：证据不足、解析失败、判断不确定，分别怎么处理？
6. **验证单项替换**：在相同输入和要求下，对比新旧结果。
7. **验证完整任务**：同时检查质量、成本、耗时和剩余的 Agent 工作量。

**更便宜、更快，但漏掉更多结果，不等于已经完成优化。** 构建和维护程序也有成本；适合重复执行的方案，不一定适合只做一次的任务。[查看完整方法](references/executor-selection.md#work-through-a-replacement)。

## 实测：网站信息处理长程任务

我们在同一个私有任务上比较了三种执行方式。两个 Codex 方案使用 Sol high；WhatToOffload 方案使用 Jev（`typesafe/jev-1.13`）和 DeepSeek-V4.1-Flash（API 别名 `deepseek-flash`），其中 DeepSeek 处理明确的异常情况。

| 方案 | 模型执行费用 | 耗时 | 完成度 / 100 |
| --- | ---: | ---: | ---: |
| Codex 直接执行 | $4.5361 | 13.14 分钟 | 92.8 |
| Codex + 任务 Skill | $3.5562 | 12.72 分钟 | 96.4 |
| WhatToOffload 设计的工作流 | $0.0472 | 3.40 分钟 | 83.2 |

![网站信息处理长程任务对比](benchmarks/results/website-long-horizon-comparison.svg)

这次实测中，工作流的执行费用和耗时更低，但完成度也低于两组基线。每组只呈现一次执行，**三组均未通过严格验收**，不能据此推断普遍成功率。完成度衡量信息覆盖情况，严格验收还检查准确性、证据和完整交付。

费用只计执行模型消耗：Codex 根据实际会话 Token 折算为 API 等价费用，构建、调试和其他未计费用不包含在表内。具体任务与原始材料只保存在本地，仓库公开匿名汇总数据。[完整报告与测量口径](benchmarks/results/website-long-horizon.md)。
